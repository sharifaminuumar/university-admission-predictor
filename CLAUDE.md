# CLAUDE.md

Project memory for the Ghanaian University Admission Predictor. Keep this file current — see **Maintenance** at the bottom.

## Project Overview

A Flask web app that predicts which Ghanaian university programs a student qualifies for from their WASSCE results. A student picks a target institution and enters core + elective grades; the app computes their Best-6 aggregate and checks it against each program's cutoff and subject-specific requirements.

Universities currently seeded (20, 1137 programmes): **UG**, **KNUST**, **UDS**, **UPSA**, **UCC**, **UEW**, **UHAS**, **UMAT**, **UENR**, **AAMUSTED**, **ATU**, **GCTU**, **ASHESI**, **VVU**, **TTU**, **KSTU**, **HTU**, **CKT-UTAS**, **SDD-UBIDS**, **CUG**.

Short codes may contain a hyphen (`CKT-UTAS`, `SDD-UBIDS`); `/api/programs/<code>` uppercases its input, so registry codes must be uppercase while `logoPath()` lowercases them for the filename.

Each university carries a **`region`** (Ghanaian administrative region) on the `University` model, returned by both API endpoints and used by the Region filter that narrows the institution dropdown in both UI modes. The region in `seed_db.py`'s `UNIVERSITIES` registry is authoritative; a data file's own `region` key is cross-checked against it at seed time and any mismatch is printed as a warning.

**Data-quality caveat worth knowing before trusting a result:** only ~12% of seeded programmes have a real published per-programme cut-off (UCC, UHAS, and two CKT-UTAS nursing programmes). Most institutions — UMaT, UENR, AAMUSTED, GCTU, TTU, KsTU, HTU, SDD-UBIDS, CUG and both private universities — publish none at all, so the large majority of programmes sit at their university's site-wide ceiling (aggregate 36, or 54 meaning "no aggregate bar" for diploma entry) — those entries mean "meets the minimum entry bar", *not* "would likely be admitted". Each school's `data/<code>_notes.md` (gitignored) records the sourcing.

This provenance is carried end to end as **`cutoff_source`**: a column on `Program`, set from the JSON during seeding, returned by both API endpoints, and rendered as a badge on every programme card. Its three values are `published` (a real per-programme cut-off), `general_ceiling` (the university's site-wide minimum, shown with an amber badge and an explicit "not a guaranteed departmental cut-off" caveat), and `unverified` (the default for the older UG/KNUST/UDS/UPSA files, which predate the field — they are *not* claimed as published). Any new data file should set `cutoff_source` explicitly.

## Core Commands

```bash
# Run the dev server (http://127.0.0.1:5000)
python run.py

# Reseed the database from data/*.json (drops and recreates all tables)
python seed_db.py
```

**Tests:** there is no test suite yet. `requirements.txt` has no test runner installed. When tests are added, prefer `pytest` and document the run command here.

## Architecture & Layout

```
run.py                  entrypoint; app = create_app(); app.run(debug=True)
seed_db.py               loads data/*.json into the DB via the app factory
app/
  __init__.py             app factory (create_app); configures instance-relative SQLite URI
  models.py               SQLAlchemy ORM: University, Program
  routes.py                Flask Blueprint ("main"): / (index), /api/predict (POST), /api/programs/<uni_code> (GET)
  eligibility_engine.py    pure functions, no Flask/DB imports — the actual prediction logic
  templates/index.html     single-page form UI (Tailwind CDN)
  static/main.js           builds grade dropdowns/elective rows, POSTs to /api/predict, renders results
  static/style.css
data/*.json               one file per university: programs + cutoff_aggregate + requirements
instance/admissions.db     canonical SQLite file (gitignored, regenerated by seed_db.py)
```

**Data flow:** `main.js` POSTs the raw form payload to `/api/predict` → `routes.py` builds a `student_grades` dict and a flattened `student_subjects` portfolio via `build_subject_portfolio()` → for each `Program` row belonging to the selected university, `evaluate_eligibility()` checks mandatory subjects/grades, then (if eligible) `calculate_aggregate()` computes that program's Best-6 aggregate → programs where `aggregate <= cutoff_aggregate` are returned as JSON.

**Six views, hash-routed** (`#home` — the default, `#predict`, `#directory`, `#calculator`, `#faq`, `#about`), wired in `main.js` via `showView()` + a `hashchange` listener. Each is a `[data-view-panel]` div in `index.html`; an unknown hash falls back to `#home`. Directory/calculator/FAQ build lazily on first open. `/api/universities` returns per-school summaries (region, counts, published cut-off range) and backs the home metrics, both marquee tracks and the directory.

**Header + drawer.** Nav links are right-aligned next to the theme toggle and shown only at `lg` (1024px+) — six items plus the logo and two buttons overflow at `md`. Below `lg` they collapse into a right-hand drawer that slides on `transform` only. `openDrawer`/`closeDrawer` resolve their elements via `drawerParts()` at call time rather than module-scope `const`s, because `showView()` calls `closeDrawer()` during boot and a `const` declared lower in the file would be in its temporal dead zone — that exact bug silently killed the whole script once.

**University logos.** `logoBadge()` renders `/static/images/logos/<shortcode>.png` in a 40px rounded container over a generated monogram; if the file is missing the `onerror` handler removes the `<img>` and the monogram underneath shows through, so a missing logo never breaks a card. **Adding a school later only needs `<shortcode>.png` dropped into that folder — no JS change.** Files are fetched by `scripts/fetch_logos.py` (dev-time only; needs `certifi` on macOS) and normalised to PNG at 160px.

Two traps that script exists to avoid, both of which produced wrong images before: a university article's *lead* image on Wikipedia is nearly always a campus photograph, and a bare `"logo"` filename match picks up `Commons-logo.svg` from the external-links section of almost every article — which silently gave nine schools the identical Wikimedia logo. The resolver therefore requires the filename to *both* name the institution and contain a logo/crest word, and rejects photo-sized downloads.

**These are the universities' real trademarked marks**, used nominatively to identify each institution. AAMUSTED and GCTU are only available as 32×32 favicons, so they look soft when upscaled. `CREST_COLOURS` still backs the fallback monograms; every pair in that map is contrast-checked, so keep new entries at AA or better.

**Metrics copy is generated, not hardcoded.** `paintMetrics()` derives the hero and home banner text from the live `/api/universities` counts and rounds programme totals **down** via `generaliseCount()`, so a claim is never an overstatement. Do not hardcode counts in copy — the figure must stay truthful as schools are added. It now legitimately reads "20 Universities · 1100+ Programmes" because the data supports it.

**Motion conventions** (follow these — they came from the `emil-design-eng` skill in `.agents/skills/`): animate **only** `transform`/`opacity`, never width/height/margin; use the custom curves `--ease-out`/`--ease-view` rather than the built-in keywords; never `ease-in` for UI; entrances start at `scale(0.97)`, never `scale(0)`; pressables get `:active { transform: scale(0.98) }` at `--dur-press` (140ms); wrap every hover rule in `@media (hover: hover) and (pointer: fine)` so mobile taps don't stick; and keep the `prefers-reduced-motion` block working. The marquee duplicates its card list and translates `-50%` with `linear` timing — the two halves must stay identical or the loop visibly jumps.

**Two UI modes inside `#predict`** (tabs at the top of the main card, wired in `main.js` via `activateMode()`):
- **Check Eligibility** — the grade form → `/api/predict`. Results carry a client-side search box that filters the rendered cards by program name.
- **Browse Programmes** — no grades needed. Picking an institution calls `GET /api/programs/<uni_code>`, which returns every program for that university with its raw `cutoff_aggregate` and `requirements`, rendered as a searchable catalogue. Returns 404 for an unknown short code; the code is matched case-insensitively.

Both searches filter in-memory arrays (`lastEligiblePrograms`, `browsePrograms`) and re-render — no server round-trip per keystroke. Each mode only ever shows its own results section.

**Near Miss and improvement tips.** `/api/predict` also returns programmes whose *subject* requirements are met but whose aggregate misses the cut-off by up to `NEAR_MISS_WINDOW` (3) points. These carry `"eligible": false` and band `"Near Miss"`, sort last, and render with an explicit "you do not qualify yet" notice — they must never read as a pass. Each Near Miss, and each `Competitive` programme, also carries an `improvement` object from `suggest_improvement()`: the smallest single-subject grade upgrade that would make the student eligible (or reach the Safe band). Programmes failing on *subject* requirements are excluded entirely, since no grade upgrade fixes a subject you never sat. `Reach` programmes get no tip — that band comes from the cut-off being unpublished, not from the student's grades, so no upgrade can move it.

**Shareable URLs.** `main.js` hydrates the form from query params (`uni`, `eng`, `math`, `sci`, `soc`, `elecN_name`, `elecN_grade`) and auto-runs the prediction when at least six fields are present. Hydration only accepts values that exist as `<option>`s, so a hand-edited link cannot inject unselectable state. The Share button rebuilds that URL, copies it, and mirrors it into the address bar via `history.replaceState`.

**Open-entry cut-offs.** Diplomas store `cutoff_aggregate: 54` to mean "no aggregate bar". Cards render that as **"Open"** (with margin shown as "—") via `formatCutoff()`/`isOpenEntry()` — a literal "54" reads as a real threshold to a student.

**Printing.** An `@media print` block in `index.html` drops the nav, form, tabs, filters and footer, forces light colours regardless of theme, collapses the results grid to one column, and prevents cards splitting across pages. Anything that should never print carries `.no-print`.

Both card types render their subject requirements through the **same** `requirementsSection()` helper in `main.js`, so the two views can't drift apart visually. It emits three groups — Required cores, Required electives, and (only when present) an "Any N of these" group for `elective_options`. `/api/predict` therefore returns each programme's full `requirements` blob alongside the verdict.

**Theming (light/dark).** Every colour in the Tailwind config resolves to a CSS custom property (`"primary": "var(--color-primary)"`), and the light/dark values live in `:root, .light { … }` and `.dark { … }` blocks in `index.html`. Switching themes therefore only swaps variables on `<html>` — **do not add `dark:` variants to markup**, and do not use raw palette classes (`bg-white`, `bg-red-50`, `text-green-700`) since those don't adapt. Use the semantic tokens instead: `surface`, `surface-container-lowest/low/highest`, `on-surface`, `on-surface-variant`, `primary`, `on-primary`, `outline-variant`, `success`/`success-container`/`on-success-container`, `error-container`/`error-container-strong`/`error-outline`/`on-error-container`. Note that `text-white` on a `bg-primary` element is wrong in dark mode (primary becomes light blue) — pair it with `text-on-primary`.

Theme resolution order: saved `localStorage['edupredict-theme']` → OS `prefers-color-scheme` → light. An inline script in `<head>` applies the class before first paint to avoid a flash; `main.js` owns the toggle button and only writes to `localStorage` once the user explicitly picks a theme (so the app keeps following the OS until then). `.dark` also sets `color-scheme: dark` so native select menus and scrollbars render dark. Opacity modifiers (`bg-primary/50`) will not work on these `var()`-based colours.

**`eligibility_engine.py`** is the algorithmic core, deliberately decoupled from Flask and the DB so it stays independently testable:
- `build_subject_portfolio(student_grades)` — flattens the raw "Elective N / Elective N Grade" form keys into a single `{subject_name: grade}` map.
- `evaluate_eligibility(student_grades, program_data)` — validates mandatory cores/electives and minimum grades; returns `(is_eligible, reason)`. It also enforces the optional **`elective_options`** block, which expresses "any N of these subjects" requirements that `mandatory_electives` cannot: `{"subjects": [...], "minimum_required": 3, "minimum_grade": "C6"}`. Use it for OR-shaped rules — UHAS Medicine ("any three of Chemistry, Biology, Physics and Elective Mathematics") and UMaT's substitutable third elective ("Chemistry **or** Applied Electricity **or** Electronics", `minimum_required: 1`). Without it those programmes are badly wrong in opposite directions: Medicine wrongly accepted a General Arts student, and UMaT wrongly ignored the substitute entirely. **Every subject named in `elective_options.subjects` must also exist in `electivesList` in `main.js`** — same rule as `mandatory_electives`, or the alternative is unselectable and silently becomes a false negative.
- **`core_minimum_grade`** (optional, default `"C6"`) relaxes the threshold for the three universal cores. It accepts **any** grade, not just D7: TTU's Diploma of Technology entry is "passes A1–**E8**", so those rows use `"E8"`, and CUG's diplomas require *credit* passes and therefore keep the C6 default. Encode what the source says rather than assuming every diploma is D7 — tightening E8 to D7 wrongly rejects real applicants, and loosening C6 to D7 wrongly admits them. Diploma/HND entry in Ghana is advertised as "Passes (A1–D7)" in the cores but "a minimum of C6" in the electives, so this key affects **cores only** — elective checks always require a credit. A per-subject `minimum_grade` inside `mandatory_cores` still wins over it. All 61 diploma programmes set `"core_minimum_grade": "D7"`. Two data rules follow from this and must hold together: a diploma's `mandatory_cores` entries must also be `D7` (an explicit `C6` there silently cancels the relaxation), and its `cutoff_aggregate` must be `54` (effectively "no aggregate bar"), because one D7 plus five C6 already totals 37 — a 36 ceiling makes D7 entry arithmetically impossible.
- `classify_band(student_aggregate, cutoff_aggregate, cutoff_source)` — returns `(band, margin)` where `margin = cutoff - aggregate`. `Safe` is `margin >= 3`, `Competitive` is `0 <= margin < 3`, and **any `general_ceiling` programme is forced to `Reach`** regardless of margin, because clearing an invented ceiling says nothing about the real departmental cut-off. `/api/predict` returns `band` and `margin` and sorts safest-first.
- `calculate_aggregate(student_subjects, program_data)` — computes the Best-6 aggregate. **Important:** the 3rd core subject depends on the program's `requirements.elective_category_pool` — `"Sciences"` always uses Integrated Science, anything else (`"Any"`, etc.) uses `min(Integrated Science, Social Studies)`. This must be computed **per program**, not once globally, since different programs in the same request can have different pools.

**Models (`app/models.py`):**
- `University` — `name`, `short_code` (e.g. `"UG"`, `"KNUST"`) — matched against the frontend's `university_code` value.
- `Program` — belongs to a `University`; `cutoff_aggregate` (int); `requirements` is a Python dict transparently (de)serialized to/from a JSON text column (`_requirements`). This lets each program have arbitrary requirement shapes (`mandatory_cores`, `mandatory_electives`, `elective_category_pool`) without schema migrations.

**Database path:** the canonical SQLite file is **`instance/admissions.db`**, resolved via Flask's `instance_relative_config=True` + `app.instance_path` in `create_app()` (`app/__init__.py`) — this makes the path stable regardless of the working directory the app is launched from. Never hardcode a different `sqlite:///...` path. A stray root-level `admissions.db` should not exist; if one appears, it's safe to delete (it's gitignored and fully regenerable via `python seed_db.py`).

## Deployment (Render)

Deployed to **Render** as a Python web service, configured declaratively by `render.yaml` (a Render Blueprint) at the project root:

- **Runtime:** `python`, served by **gunicorn** (`gunicorn run:app`) — not the Flask dev server. `run.py` guards `app.run(debug=True)` behind `if __name__ == '__main__'`, so debug mode never activates under gunicorn.
- **Bind address:** the start command deliberately passes no `--bind`. Gunicorn defaults to `0.0.0.0:$PORT` whenever a `PORT` env var is present, which is exactly what Render sets and requires. Adding an explicit `--bind 127.0.0.1:8000` would make the service unreachable.
- **Build command:** `pip install -r requirements.txt && python seed_db.py`

**Ephemeral filesystem — the important part.** Render's filesystem does not persist across deploys. `instance/admissions.db` is therefore treated as a **build artifact, not stored state**: `seed_db.py` runs during the *build* phase so the seeded SQLite file is baked into the deploy image, and every deploy regenerates it from `data/*.json`. Consequences:

- `data/*.json` is the single source of truth for all program data in production. To change what's live, edit the JSON and redeploy — never mutate the deployed DB.
- The app must never write user data to SQLite expecting it to survive; anything written at runtime is lost on the next deploy. If persistent writes are ever needed, that requires a real managed database (e.g. Render Postgres), not the current SQLite file.
- `seed_db.py` calls `db.drop_all()` first, so seeding is fully idempotent.
- `seed_db.py` resolves `data/*.json` with paths relative to the **current working directory**; Render runs build commands from the repo root, so this works — but keep it in mind if the build command is ever wrapped or relocated. (`instance/admissions.db` itself is resolved absolutely via `app.instance_path` and is cwd-independent.)

## Developer Rules

- **Encoding:** all text files (`.py`, `.md`, `.json`, `.txt`, `.gitignore`, etc.) must be UTF-8. This repo previously had `.gitignore`/`README.md`/`requirements.txt` corrupted as UTF-16, which silently broke `.gitignore` pattern matching — verify with `file <path>` if anything seems off.
- **Never track compiled/generated artifacts:** no `*.pyc`, `__pycache__/`, or `*.db`/`*.sqlite3` files in git. `.gitignore` already excludes these; don't force-add over it.
- **Git commits are manual only.** Claude must never run `git commit` or `git push`. Always propose the exact `git add`/`git commit -m "..."` commands and let the user run them.
- When adding a new university, follow the runbook: **(1)** add `data/<code>.json` (plus a `data/<code>_notes.md` documenting sourcing), **(2)** add one tuple to the `UNIVERSITIES` list at the top of `seed_db.py` — it loops over that list, so no per-school code block is needed and a missing data file is skipped with a warning rather than crashing, **(3)** add one entry to the `UNIVERSITIES` constant at the top of `app/static/main.js`. That constant is the single source of truth for the frontend — both dropdowns (eligibility + browse) and the results header are built from it, so there is no hardcoded `<option>` list in `index.html` or a per-school `if` branch to update. Short codes must be UPPERCASE in both places.
- Any elective subject named in a program's `mandatory_electives` must also exist in the `electivesList` array in `main.js`, or students can never select it and that program becomes unreachable. Cross-check after adding a school.
